# 2026-11-22 - Software RAID 5 with mdadm on srv-lab-01

**Context:** Built a software RAID 5 array with `mdadm` on three virtual disks, made it persistent across reboots, then simulated a disk failure and rebuilt the array. Lab carried out from 2026-11-21 to 2026-11-22 on the Ubuntu Server 24.04 LTS VM in VirtualBox. Before starting, the VM was moved from the host's C: drive (only 4 GB free) to the E: drive with VirtualBox's Move function.

**Safety:** VirtualBox snapshot "PreRAID" taken with the VM powered off and verified in the snapshot list (the old "PreNewSSHKey" snapshot was deleted). Backups of `/etc/mdadm/mdadm.conf` and `/etc/fstab` copied to `~/backups/` before editing. The new disks were empty, so creating the array could not destroy data.

**Actions:**

*Preparation*

Three 1 GB dynamically allocated disks (`raid-disk1`, `raid-disk2`, `raid-disk3`) added to the SATA controller in VirtualBox, stored on the E: drive.

```bash
lsblk
mdadm --version
```

- The new disks appear as `sdb`, `sdc` and `sdd` (1 GB each, no partitions). VirtualBox file names are not visible to Linux; disks are named in order.
- `mdadm` v4.3 already installed.

*Creating the array*

```bash
sudo mdadm -C /dev/md0 -l 5 --raid-devices=3 /dev/sdb /dev/sdc /dev/sdd
cat /proc/mdstat
sudo mdadm --detail /dev/md0
```

- `/proc/mdstat`: `md0 : active raid5`, `[3/3] [UUU]` (three of three disks up).
- `mdadm --detail`: array size 2044 MiB, i.e. (3 − 1) × 1 GB; `State : clean`; 3 active, 3 working, 0 failed, 0 spare. The initial sync finished in about 8 seconds.

*File system and mount*

```bash
sudo mkfs.ext4 /dev/md0
sudo mkdir /mnt/raid
sudo mount /dev/md0 /mnt/raid
df -h
cd /mnt/raid
sudo nano test.md
sudo cat test.md
```

- `df -h`: `/dev/md0` 2.0G size, 1.9G available (file system metadata, journal and the 5% reserved for root).
- Test file `test.md` written to the array.

*Persistence across reboots*

```bash
sudo cp /etc/mdadm/mdadm.conf ~/backups/
sudo mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf
tail /etc/mdadm/mdadm.conf
sudo update-initramfs -u
sudo blkid /dev/md0
sudo cp /etc/fstab ~/backups/
sudo nano /etc/fstab
sudo findmnt --verify /etc/fstab
sudo umount /mnt/raid
sudo mount -a
sudo dmesg | tail
sudo systemctl daemon-reload
```

- `mdadm.conf`: added `ARRAY /dev/md0 metadata=1.2 UUID=c019e098:...`, so the array is always assembled as `md0`.
- `update-initramfs -u`: the boot image contains a copy of `mdadm.conf` and has to be regenerated.
- Two different UUIDs: `c019e098...` identifies the array (mdadm), `73939b15...` identifies the ext4 file system (blkid).
- Line added to `/etc/fstab`: `UUID=73939b15-87ac-4d47-878c-d4f1a543cea9 /mnt/raid ext4 defaults,nofail 0 2`.
- Reboot test: after `sudo reboot`, `/proc/mdstat` shows `md0` with `[UUU]`, the array is mounted on `/mnt/raid` automatically and `test.md` is intact.

*Disk failure and rebuild*

Simulated failure of `sdd`:

```bash
cat /proc/mdstat
sudo mdadm /dev/md0 --fail /dev/sdd
cat /proc/mdstat
sudo mdadm --detail /dev/md0
cat /mnt/raid/test.md
```

- `/proc/mdstat`: `sdd[3](F)` marked faulty, `[3/2] [UU_]`.
- `mdadm --detail`: `State : clean, degraded`; 2 active, 2 working, 1 failed, 0 spare; slot 2 `removed`, `sdd` listed as `faulty`.
- No rebuild started: there was no spare disk to rebuild onto.
- `test.md` still readable: the missing blocks are recalculated from parity.

Disk replacement (the same disk re-added, standing in for a new one):

```bash
sudo mdadm /dev/md0 --remove /dev/sdd
cat /proc/mdstat
sudo mdadm /dev/md0 --add /dev/sdd
watch cat /proc/mdstat
cat /proc/mdstat
sudo mdadm --detail /dev/md0
sudo dmesg | grep md0
cat /mnt/raid/test.md
```

- `--remove`: `hot removed /dev/sdd`, array still `[UU_]` with `sdd` gone from the list.
- `--add`: the recovery started on its own and finished before `watch` could show the progress; the array is back to `[UUU]`.
- Kernel log (`dmesg`), in seconds since boot: array assembled with 3 of 3 devices at boot (5.1 s) and file system mounted by `fstab` (16.4 s); `Disk failure on sdd ... Operation continuing on 2 devices` (463.9 s); `recovery of RAID array md0` (648.2 s); `recovery done` (654.4 s), about 6 seconds for 1 GB.

**Verification:** After the rebuild, `mdadm --detail` shows `State : clean` with 3 active, 3 working, 0 failed devices; `/proc/mdstat` shows `[UUU]`; `test.md` was readable before the failure, while degraded and after the rebuild. The `Events` counter went from 22 to 46, one event per state change.

**Issues:**

- The host's C: drive had only 4 GB free after the snapshot. The snapshot's differencing disk grows while the VM runs, and a full disk would pause the VM and risk corrupting it, so the whole VM was moved to the E: drive first (slower mechanical disk, acceptable for a lab).
- First `mdadm --create` drafts had a wrong level syntax (`-l=raid 5`) and an extra word after the device name; checked before running, since creating an array wipes the disks.
- `sudo mdadm --detail --scan >> /etc/mdadm/mdadm.conf` would fail: the redirection is done by the user's shell, not by `sudo`. Used `sudo tee -a` instead.
- `/etc/fstab` option written as `default` instead of `defaults`: `findmnt --verify` reported no errors, but `mount -a` failed with a generic error; `dmesg` showed `ext4: Unknown parameter 'default'`. Fixed before any reboot.
- `cd mnt/raid` from the home folder failed: relative path instead of the absolute `/mnt/raid`.
- `sudo mdadm md0 --fail sdd` failed (`error opening md0`): device names need the full path (`/dev/md0`, `/dev/sdd`). A second attempt used `/mnt/raid`, which is the mount point of the file system, not the array device.

**Lessons learned:**

- RAID 1 writes the same data to two disks at the same time (mirroring). RAID 5 stripes data across all disks with one parity block per stripe, rotating between disks: usable space is (n − 1) × disk size, and it survives one failed disk.
- Parity is calculated with XOR: from the remaining data block and the parity block, the missing block can be recalculated (A = B XOR parity).
- After a failure a RAID 5 array runs degraded: the data is still readable, recalculated from parity, but slower and with no protection left until the rebuild completes. Rebuilds on large disks can take hours.
- This is software RAID: the Linux kernel (`md` driver) creates the virtual device `/dev/md0`. A hardware RAID controller is a dedicated card, and the operating system only sees the logical disk.
- `/dev/md0` is a device file, not a folder; its content is reached through the mount point. A busy mount point (a shell inside it) cannot be unmounted.
- Persistence needs three pieces: `mdadm.conf` for a stable array name, the initramfs for boot, and `fstab` for mounting. `fstab` uses the file system UUID, which does not change if a device name does; `nofail` lets the system boot even if the array is missing.
- A syntax check (`findmnt --verify`) does not replace a real test (`mount -a`), and the kernel log (`dmesg`) usually names the exact cause of a generic error.
- When a disk fails, the array state changes from `clean` to `clean, degraded`, and `/proc/mdstat` shows the missing disk as `_` (`[UU_]`). The data stays available, but there is no protection until the rebuild completes.
- A rebuild needs a target disk. With no spare in the array, nothing happens until a replacement is added; with a spare disk configured, `mdadm` starts the rebuild on its own.
- The failed disk is removed and replaced while the array keeps running (hot swap), so the service stays available during the replacement.
- The kernel log records the whole life of the array: assembly at boot, the failure, and the start and end of the recovery, with timestamps.
